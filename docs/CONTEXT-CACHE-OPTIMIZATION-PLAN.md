# 模型缓存与上下文效率方案（已确认并实施）

用户已确认按 A–E 执行，并要求完成网关启动与 UI 实测后发版、push。目标内核已推进至 OpenClaw 2026.10.6。下面保留实施前的基线和验收要求；实施结果见 [前阶段审查](REVIEW-2026.1022.0.md) 与 [10.6 适配审查](REVIEW-2026.1023.0.md)。

## 1. 先明确优化目标

降低完成同一任务所需的未缓存输入、工具往返和首 token 延迟，同时保留结果质量、用户指令、权限和会话隔离。不能通过填充无关文本、强行维持超长历史或高频付费心跳制造漂亮命中率。

模型服务端的提示词缓存、OpenClaw 的提示词/工具目录快照、Electron/Node 的编译缓存是三件事。前两者影响模型成本与上下文效率，第三者影响网关启动。20 秒启动目标在网关性能验收中单独统计，不拿模型缓存命中率解释启动时间。

## 2. 当前项目取证

### 2.1 内置技能

以下为仓库当前文件的实测字符和 UTF-8 字节，**不是 tokenizer 得出的 token 数**。

| 内置技能 | SKILL.md 字节 | 描述字符 | 行数 |

| cryoclaw-theme-studio | 9,167 | 265 | 69 |
| officecli-docx | 13,253 | 403 | 263 |
| officecli-pptx | 16,227 | 663 | 293 |

| openclaw-and-cryoclaw-manual | 6,354 | 876 | 134 |
| 合计 | **64,365** | **2,928** | **1,095** |

不能把 64 KB 当作每轮必传：常驻目录主要是名称、描述与位置，正文按需读取。当前真正可优化的是描述过长、正文夹带大量条件性操作细节，以及一次加载后不必要地留在历史中的说明。OpenClaw 文档也明确区分目录注入与正文按需加载。[上下文构成](https://docs.openclaw.ai/concepts/context)

### 2.2 用户侧只读快照

- 当前主模型是 `deepseek/deepseek-flash`；备用链首项再次包含同一模型。这是可检查的冗余，**本轮尚未更改用户选择**。
- 工作区 AGENTS.md 10,965 B、SOUL.md 2,148 B、IDENTITY.md 329 B、USER.md 966 B、MEMORY.md 3,632 B，合计 18,040 B。只记录大小，没有把这些私人正文复制进仓库。
- 当前 compaction 为 `safeguard`；heartbeat 为 3 小时，并限定 09:00–23:00。没有为了缓存而更改它。
- 这些文件与插件是否进入某一次模型请求，必须依据该次原生 `/context detail` / systemPromptReport 确认，不能只按磁盘大小推断。

### 2.3 10.5 内核已经具备的能力

对实际 npm 产物进行了静态取证，暂存证据在 `.cache/context-forensics/`，不作为最终发布资产：

- `attempt-system-prompt-prepare-*.mjs` 已区分稳定提示词与动态后缀，计算 section/history/tool 指纹，记录 historyRewrite、aggregateToolResultTruncation 等失效原因；工具诊断快照也已有稳定排序。应复用这些能力，而非再做一套不兼容提示词重写器。
- `prompt-cache-retention-*.mjs` 按提供商、API 与 compat 能力决定是否接收 retention；不能给所有“兼容 OpenAI”的地址统一加字段。
- `@openclaw/ai/dist/openai-prompt-cache-*.mjs` 已对支持的较新 OpenAI 模型使用不同的 lifetime 字段。当前官方文档也区分新旧模型，不能机械套用旧文章中的 `prompt_cache_key` / `24h` 配置。[OpenAI 提示词缓存](https://developers.openai.com/api/docs/guides/prompt-caching)
- 当前 DeepSeek 所走的兼容传输将缓存读取映射为 `cacheRead`，并从原始 prompt 输入中扣除 cacheRead/cacheWrite，得到未缓存 `input`。因此该标准化结构的输入分母应为 `input + cacheRead + cacheWrite`，不能只用 input。
- 直接工具结果进入该传输时只序列化 `toolMsg.content`；交付插件返回一句短确认，元数据放在原生 `details`。实测补充：10.5 Code Mode 的 `API.call` 会把 details 投影为 guest 返回值，若模型 return 该值，路径等元数据仍会进入 exec 结果。原生 `openclaw.nested-tool.v1` 独立回执标记 excludeFromContext，UI 现在直接识别该回执；不再要求模型输出长协议，不读正文、不生成 base64，不能将“details 永不进入模型”作为跨运行模式保证。
- 现有用量页已有 cacheRead/cacheWrite 数据模型，但主要统计卡与部分兜底加总尚不能完整解释缓存收益；聊天底部的统计也缺少缓存分项及“未知”状态。

## 3. 建议确认的实施范围

### A. 先建立可解释的测量层（最高优先级）

1. 统一提供商 usage 归一化，保留“缺失/未知”与“明确为 0”的区别。避免重复计算 prompt/input 与 cacheRead。
2. 用量页增加缓存读取、写入、未缓存输入、加权读取比例和可用成本；聊天会话信息提供轻量查看入口。按提供商/模型/API 分组，不混算不同价格与不同缓存机制。
3. 基于 10.5 原生指纹报告，展示本地诊断原因：模型/API 变更、工具 schema 变化、稳定区变化、历史重写、压缩、会话重置、重试/回退及请求间隔。无法证明原因时标为未知。
4. 默认不记录提示词、文件内容、密钥或完整请求。诊断只保存摘要、长度、section 名、次数和耗时，设置容量上限和一键清理。

涉及：`chat/message-meta.ts`、`views/settings/tab-usage.lib.ts` / `tab-usage.ts`、`controllers/usage-cache.ts`，以及原生诊断的只读适配。若内核未暴露某项数据，先增加受测的最小读取接口，不猜测内部对象布局。

### B. 稳定可复用前缀，控制有原因的失效

1. 审查 CryoClaw 自己添加的提示词、工具 schema、技能目录与运行时上下文；相同输入、相同配置的序列化必须稳定。
2. 常量能力说明保持固定顺序；当前时间、UI 状态、临时任务进度、一次性诊断放到原生允许的动态后缀或当前轮消息。
3. 不因为流式重绘、余额刷新或仪表盘切换而写模型配置/重建工具目录。不把 UI 缓存当成服务端缓存收益。
4. 配置保存只在内容实际变化时失效。新增/删除工具、修改技能、切换模型、修改权限时必须正常失效，不能靠陈旧缓存隐藏真实变更。
5. 历史以追加为主；不要反复改写已发送的工具结果或为了节省 UI 展示而删除模型需要的上下文。原生 compaction、明确 reset 和安全清理仍由内核处理。

涉及：CryoClaw 的 provider/config 写入路径、内置插件/技能注入、原生 prompt-cache 接口边界；采用最小兼容补丁并同步打包与运行时升级器。

### C. 重构 5 个内置技能，正文按需展开

1. 描述聚焦“何时使用”，去掉长例子、重复关键词和通用能力说明；目标将目前 2,928 描述字符降低约 40%–60%，以正确触发为硬约束。
2. Office 三技能的入口只保留路由、输入/输出约定、不可丢的质量要求；长命令表、复杂版式和特殊操作移入 references，明确何时读取。
3. Theme Studio 保留 inspect → 生成 → preview 的必要安全与操作约束，减少在主入口中重复的说明；预览票据、错误输出不进入常驻目录。
4. 手册技能改为短触发与检索路由，避免宽泛触发拖慢无关任务；保留对产品事实进行取证的要求。
5. 交付功能保持插件形态，不再新增交付技能。工具 schema 当前序列化为 **322 个字符**，成功结果正文与文件数量基本无关，UI 元数据不进入本传输的模型正文。

涉及：`builtin-skills/*/SKILL.md` 与按需 references。验证 Office 生成/修改、手册问答、主题预览、文件交付的真实用例；不能只看文件变短。

### D. 按提供商能力配置，不做全局强制开关

| 路线 | 建议 |
|---|---|
| DeepSeek（当前主模型） | 保持自动前缀缓存，优先稳定请求和测量命中/未命中字段；不伪造一个通用的 retention 参数。自动缓存仍由服务端控制。[官方规则](https://api-docs.deepseek.com/guides/kv_cache/) |
| Anthropic / 已验证的 Anthropic 兼容路线 | 根据真实访问间隔与能力选择 short/long；长保留会改变写入成本，不能默认一律拉满。 |
| OpenAI 原生 Responses | 复用 10.5 的 API/模型能力判断；新旧模型的参数不同。支持时可增加原生 cache diagnostics 只读诊断，不把官方 API 能力套到 ChatGPT/Codex 登录后端。[诊断](https://developers.openai.com/api/docs/guides/prompt-caching/diagnostics) |
| Kimi、MiMo、Qwen、代理服务 | 逐项检查真实 endpoint 与 SDK 支持；不凭“兼容 OpenAI”推断缓存、计费、TTL 或缓存 key 支持。缺乏服务端字段时显示未知。 |

具体 retention 的适用边界以 10.5 实际代码与提供商当前规则交叉验证。[OpenClaw 提供商缓存适配](https://docs.openclaw.ai/reference/prompt-caching)

### E. 长任务的上下文预算

1. 分别统计系统说明、技能目录、已加载技能、工具 schema、历史、工具结果和图像。使用原生 `/context` 报告；没有真实 tokenizer 时只显示字符/字节或明确标注估算。
2. 重工具输出提供短摘要与落盘产物引用，保留继续查阅原始结果的路径。不要把全文、base64、截图说明重复带入每一轮。
3. 保持原生 safeguard compaction；先观测压缩前后任务质量，再讨论阈值。禁止按单次命中率自动删除历史。
4. 备用链检查重复模型，但保留用户指定的跨提供商回退目的。切换 provider/model 本来就可能丢失缓存，不以缓存为由关闭必要回退。
5. 对用户 AGENTS/MEMORY 等私人上下文，先给单独的瘦身建议；本次确认默认只覆盖项目内的技能和代码，**不自动改写私人记忆或角色文件**。

## 4. 验收方式

### 正确性

- 相同配置的稳定提示词与工具 schema 指纹连续重复完全一致；真正改变配置后能够失效。
- usage 夹具覆盖 DeepSeek 命中/未命中、原生 OpenAI、Anthropic read/write、缺字段、0 值、多轮求和和 provider 回退。
- 插件调用 + 文字协议混用只产生一份同文件卡片；失败工具、不同文件、新轮次和用户附件不被错误抑制。
- 技能瘦身后复跑真实任务，保留必要引用、安全限制和输出质量。

### 效率

- 用固定 QA 会话做冷请求、短间隔追加、工具结果追加、技能读取、重连、压缩、模型回退的对照；只用已经配置的提供商。
- 同时记录未缓存输入、cacheRead/cacheWrite、首 token 延迟、总延迟、请求次数和成功任务成本。未知字段不填 0，不声称缓存命中可保证。
- 优先完成离线载荷/指纹测试；在线测试有固定请求上限，不靠重复空转或付费心跳“保温”。
- 网关另做原地安装路径下的首次迁移、普通冷启动和热启动矩阵；逐次报告首轮成功与是否在 20 秒内。首次 schema 迁移不计入正常启动指标，但单独报告迁移耗时与失败原因。

## 5. 发布和恢复

确认后按 A → B/C → D/E 实施，每阶段记录前后数据；能力不支持时保留原生路径。配置改动保留快照，新的界面和诊断可回退。全部回归、实际升级数据库、真实交付/仪表盘、完整 UI 与真实消息验收通过后，再更新版本说明、生成最终三件套、草稿校验、push 和正式发布。

推荐确认 **A–E 全部实施**，其中 D 仅对检测确认支持的现有提供商生效，E 不包含自动改写私人记忆文件，也不改变现有心跳周期。
